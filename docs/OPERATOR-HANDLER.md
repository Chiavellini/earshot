# Operator handler — gated design (approved 2026-07-29; v1 human-first BUILT, v2 clips/classifier NEXT)

**Problem (VERIFICATIONS Q-ADMIT / Q-OPS):** MSFT, CVNA, and WING route their
dial-ins through LIVE OPERATOR SCREENS — a human asks who you are and
disconnects a silent line in 21–73 s. These venues are unattended-infeasible
under the pure listen-only posture, and per the 2026-07-29 decision, webcast is
not an acceptable fallback where a phone bridge exists. The user approved a
FULL, GATED build of a clip-based operator responder — and, same day, signed
off on shipping the HUMAN-FIRST variant first: the clip/classifier build below
becomes **v2**, answered by the same conference topology.

## v1 — human-first (BUILT 2026-07-29, `control.operator`; wire pins PENDING)

When we dial a Class B bridge, the call is placed into a named Twilio
`<Conference>` that carries our media fork, and the USER'S CELL is paged into
the same conference BEFORE the bridge dial. The user answers the operator's
questions by voice; after admission the user hangs up and the bridge leg +
stream persist for the whole call.

- `scripts/operator-page.sh` — originates the cell leg FIRST
  (`<Say>` + `<Dial><Conference startConferenceOnEnter="true"
  endConferenceOnExit="false">`); destination is EXACTLY the config's
  `cell_number`, any other `--to` refused; `--wait-joined <secs>` polls the
  Calls API and exits nonzero unless the page was ANSWERED — the orchestrator
  never dials a bridge unmanned. Pages via `scripts/notify.sh` too when present.
- `scripts/twilio-operator-dial.sh` — dials the bridge with
  `<Start><Stream track="inbound_track">` `[<Play digits>]`
  `<Dial><Conference beep="false" startConferenceOnEnter="false"
  endConferenceOnExit="true" waitUrl="">` — the bridge hears silence until the
  human is present, the conference dies with the bridge leg, and the fork
  carries ONLY the bridge's inbound audio (the user's voice rides the outbound
  track and never enters the pipeline — the Q-CONF hypothesis, pinned before
  any live use). Never `<Number>/<Sip>/<Connect>/<Say>/<Record>`.
- **Double gate:** `[operator_handler] enabled = true` in the event config
  (`src/config.rs`, validated E.164 `cell_number` + `[a-z0-9-]{1,24}`
  `conference_prefix`) AND `--operator-i-am-paged` on every operator script.
- Invariants frozen by `tests/twilio_operator_gated.rs`, which ALSO re-asserts
  the default `scripts/twilio-dial.sh` TwiML contains no
  `<Connect>/<Dial>/<Number>/<Sip>`.

**Everything below the Phase-0 section is the v2 spec (clips + classifier +
duplex stream). It is unchanged in scope; only the ordering moved.**

## Non-negotiable framing

The listen-only invariant (`docs/TWILIO.md`, `tests/twilio_listen_only.rs`)
stays exactly as it is. The operator handler is a SEPARATE, explicitly-gated
path with its own invariant and tests (all of these EXIST as of v1):

- Config section `[operator_handler]`, `enabled = false` default
  (`src/config.rs`); the operator TwiML additionally requires the explicit
  `--operator-i-am-paged` CLI flag at dial time.
- Operator TwiML is generated by a NEW script (`scripts/twilio-operator-dial.sh`)
  — never a branch inside `scripts/twilio-dial.sh`. The default
  dial path remains provably byte-identical.
- v2 only: the handler may speak ONLY pre-recorded clips from `clips_dir`;
  there is no TTS, no free-form audio synthesis, no DTMF beyond the existing
  charset. (In v1 nothing on our side speaks toward the bridge at all — the
  human is on a separate conference leg.)
- The pager/human leg may `<Dial>` ONLY the configured `cell_number`
  (`scripts/operator-page.sh` refuses any other `--to`).
- Invariant test `tests/twilio_operator_gated.rs`:
  default path contains no `<Connect>/<Dial>/<Number>/<Sip>`; operator TwiML
  unreachable unless double-gated; bridge leg is
  `<Start><Stream track="inbound_track">` + `<Dial><Conference>` with no
  `<Number>/<Sip>/<Connect>/<Say>/<Record>`; pager dial target constrained to
  the configured cell; DTMF charset unchanged.

## Phase 0 — wire-fact pins (BLOCK all LIVE use; ~$1 of probe calls)

Per the VERIFICATIONS discipline, the unknowns must be pinned live before any
operator dial touches a real bridge. Status as of 2026-07-29: **probe scripts
exist and are runnable; NO pin has been executed yet.**

1. **Q-CONF** (v1's load-bearing pin — `scripts/probe-q-conf.sh`, EXECUTION
   PENDING) — does a `<Start><Stream track="inbound_track">` fork survive and
   keep carrying the far end's audio while the call sits in
   `<Dial><Conference>`, and does the OTHER conference participant's voice
   (the paged human) stay OFF the inbound track? Step 1 runs unattended
   against the TTS rehearsal number; `--with-cell` adds the human marker-phrase
   test. Both destinations are hard-allowlisted.
2. **Q-UPDATE** (`scripts/probe-q-update.sh`, EXECUTION PENDING) — does
   `POST /Calls/<sid>.json` with replacement TwiML kill a running
   `<Start><Stream>` fork? Decides whether mid-call REST re-steering ("listen
   + occasionally play a clip by REST update", v2) is even possible.
3. **Q-CONNECT** (DEFERRED TO v2 — no script yet) — bidirectional
   `<Connect><Stream>` semantics: outbound media message format (base64 μ-law
   `media` + `mark`), whether the inbound track still arrives on the same WS,
   TwiML blocking behavior, and — critical — how to hand off to plain
   listen-only capture after admission (stay duplex for the whole call vs
   REST-swap back to `<Start><Stream>`). v1 does not need it: the human
   speaks over the PSTN conference, not over a duplex stream.
4. **Q-FALLBACK** — RESOLVED BY DESIGN 2026-07-29: v1 IS the fallback
   mechanism, promoted to the primary path (originate the bridge leg into a
   named `<Conference>` + page the user's cell into the same conference).
   Its wire behavior is exactly what Q-CONF pins.

The pins decide, not memory. Run everything against our own numbers (TTS
rehearsal number + the fake operator below) — never a real bridge.

## v2 architecture — clip responder (after pins; adjust to what they say)

- `src/operator/` — state machine
  `AwaitOperator → Answering{intent} → Holding → Admitted → Escalate`.
- Intent classifier (`src/operator/intents.rs`): keyword/regex over ASR text —
  name / spell-name / company / conference-name / mute-check / hold / reject /
  admitted cues. Seed patterns from the 2026-07-29 INCOM + Chorus transcripts
  (`corpus/bridge-probes/*.txt`) — they are labeled training data.
- ASR: faster-whisper subprocess over 3–5 s windows
  (`scripts/operator-asr.py`, `.venv-corpus`). Operator cadence is slow;
  1–2 s latency is fine. (The streaming CTC KWS is the wrong shape — closed
  vocab.)
- Duplex WS path: `src/source/twilio_ws_duplex.rs` on its OWN URL path with its
  own pinned `TWILIO_OPERATOR_STREAM_URL` (Q-M3: the signature base is the
  exact stream URL).
- Escalation: unknown intent ×2 or low confidence → "please hold" clip + page
  (mailer/push) + human-fallback leg per Q-FALLBACK. **The fallback is
  load-bearing, not optional.**
- After admission: hand off to the normal capture pipeline (mechanism per
  Q-CONNECT) and fall silent — from that moment the listen-only posture
  applies in full.

## Rehearsal harness — fake operator (BUILT with v1: `scripts/fake-operator/`)

A Twilio number we own running `<Gather input="speech">` TwiML that asks the
INCOM/Chorus questions VERBATIM from the Q-ADMIT transcripts ("may I have your
first and last name", a company question, a mute-check after 8 s of silence, a
hangup ~15 s later), then plays the TTS keyword script on successful
admission. Assets in `scripts/fake-operator/` (`server.py`, stdlib-only;
wiring + rehearsal ladder in its `README.md`). The whole ladder — screen →
human (v1) or clips (v2) → admission → detection — rehearses end-to-end for
pennies. Final gate before live use: a `launch-event.sh` rehearsal against the
fake operator with real SIGTERM, then ONE off-hours probe against a real
WING-class bridge, never near a traded event.
